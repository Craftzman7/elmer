# AGENTS.md

Guidance for coding agents working in this repository.

## What elmer is

elmer is a blue team host monitor for Red v Blue competitions: a single
static Go binary for Linux and Windows that watches a host for attacker
activity (process exec, auth, file integrity, network, persistence) and
alerts via stdout / Discord / ntfy / webhook. Two non-negotiable product
properties:

- **Zero listening sockets.** elmer only makes *outbound* HTTPS calls to
  alert channels. Never add a listener, HTTP server, or bind.
- **Single static binary.** `CGO_ENABLED=0`, no cgo, no dynamic linking.
  BPF bytecode is precompiled and embedded — the cilium/ebpf dependency
  is loader-only.

## Repository layout

```
cmd/elmer/            entry point (thin; real logic lives in internal/)
internal/cli/         cobra commands (start, audit, test-alerts,
                      init-config, harden, version)
internal/app/         pipeline wiring + per-platform buildMonitors/Harden/Audit
                      (app.go shared, app_linux.go, app_windows.go,
                       app_other.go for non-Linux non-Windows)
internal/config/      YAML config, defaults, discovery, DefaultYAML template
internal/events/      Event model, Severity, categories, dedupe
internal/detect/      detection engine + builtinRules (rules.go)
internal/monitors/    Monitor implementations, split by platform suffix
internal/monitors/ebpf/   embedded BPF objects + loader (linux-only)
internal/alert/       dispatchers: stdout, discord, ntfy, webhook + Manager
internal/util/        procfs/address/file parsing helpers
tools/ebpfcheck/      standalone "does eBPF work on this box" checker
```

Module path is `elmer` — imports look like `elmer/internal/events`.

## Build & test commands

```sh
make test          # go test ./... (host platform)
make vet           # go vet ./...
make build         # cross-compile all four targets into dist/
                   # (linux/windows × amd64/arm64) — catches build-tag
                   # breakage on the platform you're not developing on
make generate      # regenerate embedded BPF objects (see below)
```

Development typically happens on macOS, but the real targets are Linux
and Windows. Most monitor code carries `//go:build linux` or
`//go:build windows` tags (file suffixes `_linux.go` / `_windows.go`),
so **`make test` alone will not compile the other platform's code**.
After touching anything platform-specific, always run `make build` to
verify both platforms compile.

## BPF codegen

`internal/monitors/ebpf/bpf/*.c` is the only hand-written BPF source.
The compiled objects (`elmerbpf_bpfeb.o`, `elmerbpf_bpfel.o`) and Go
bindings are **generated by bpf2go and committed**. Regenerate only when
the `.c` changes:

```sh
make generate   # runs go generate in a Linux Docker container
```

It requires Docker because Apple's clang lacks the BPF target. Never
hand-edit `elmerbpf_bpfeb.go`, `elmerbpf_bpfel.go`, or the `.o` files.
No CO-RE, no vmlinux.h, no kernel headers — keep it that way.

## Architecture: the pipeline

```
monitors ──▶ events.Event chan (buffer 1024) ──▶ detect.Engine.Evaluate
                                                        │
                                                        ▼
                                                   dedupe ──▶ alert.Manager
                                                                  │
                        stdout / discord / ntfy / webhook ◀───────┘
```

Key interfaces (learn these before extending):

- **`monitors.Monitor`** — `Name()`, `Start(ctx, out chan<- events.Event)`,
  `Capabilities() []string`. Start blocks until ctx is canceled. Optional
  `io.Closer` gets called on shutdown.
- **`alert.Dispatcher`** — `Name()`, `Send(ctx, ev)`. Each runs in its own
  goroutine with a bounded queue (drop-oldest when full).
- **`detect.Engine`** — evaluates events against regex rules; monitors
  assign baseline severities and **the engine only escalates, never
  lowers**.

### Invariants to preserve when changing code

1. **The pipeline never blocks on a channel.** Dispatch uses drop-oldest
   queues so a hung webhook can't stall alerting or monitoring.
2. **Degrade loudly.** When a telemetry tier is unavailable (e.g. no root
   for eBPF), emit a `monitors.DegradedNote(...)` event rather than
   silently doing less. The Linux eBPF monitor's availability downgrades
   process/net monitors (see `app_linux.go`).
3. **Severity only escalates** through the detection engine.
4. **Monitors must work unprivileged where possible**, with graceful
   fallbacks (Linux tiering: eBPF → netlink proc connector → /proc
   polling).
5. Events carry a `Key` for dedupe identity (falls back to
   Title+Category). Set it for high-volume repeat events.

## Common tasks

### Add a detection rule

Append to `builtinRules` in `internal/detect/rules.go`. Each rule needs:
`ID` (unique, kebab-case), `Title`, `Technique` (MITRE ATT&CK ID),
`Target` (`process` | `path` | `line` | `any`), `Pattern` (Go regexp,
mind double-escaping), `Severity`. Keep patterns anchored/word-bounded
enough to avoid false positives on legitimate commands. Users can add
rules via config (`rules:`) or disable builtins (`disabled_rules:`).

### Add a monitor

1. Implement the `Monitor` interface in `internal/monitors/` using
   `_linux.go` / `_windows.go` build-tagged files (see existing monitors
   for the pattern).
2. Wire it into `buildMonitors` in both `internal/app/app_linux.go` and
   `internal/app/app_windows.go`, gated by `cfg.MonitorEnabled("<name>")`.
3. Emit `events.Event` values with an appropriate category constant and
   baseline severity.

### Add an alert channel

Implement `Dispatcher` in `internal/alert/<name>.go`, register it in
`NewManager` (gated on its config being non-empty), and honor
`min_severity` filtering. Channel config lives in
`internal/config/config.go` (`AlertsConfig`).

### Add a CLI command

Add a `cobra.Command` constructor in `internal/cli/cli.go` and register
it in `New()`. Config flags follow the existing pattern
(`-c/--config` string). Version is the `Version` var, stamped via
`-ldflags` at build time.

## Code style

- Go 1.27, stdlib-first. Only deps: cobra, x/sys, yaml.v3, cilium/ebpf.
  Do not add dependencies without strong justification.
- Every package starts with a doc comment; comments explain *why*, not
  what. Match the existing terse style.
- Platform-specific code always carries `//go:build` tags and matching
  filename suffix; shared code goes in the untagged file.
- Time durations in config are `time.Duration` parsed from YAML strings
  (e.g. `30s`). Config tri-states use `*bool` (nil = default on).
- Errors wrap with `%w` and context (`fmt.Errorf("detection engine: %w",
  err)`).

## Testing

- Standard library `testing` only, tests live in-package
  (`package alert`, not `package alert_test`).
- HTTP-facing code is tested with `httptest.NewServer` (see
  `alert_test.go` for the pattern, including HMAC signature assertions).
- Tests must pass on the dev host (macOS); platform-tagged files are
  excluded from host runs, which is another reason `make build` matters.
- No test currently requires root or eBPF — keep it that way so
  `make test` works anywhere.

## Configuration

YAML (`elmer.yaml`), discovery order: `-c` flag → `$ELMER_CONFIG` →
`./elmer.yaml` → `/etc/elmer/elmer.yaml` (`C:\ProgramData\elmer\
elmer.yaml` on Windows). No file = built-in defaults (`config.Default()`).
The commented template users get from `elmer init-config` is
`config.DefaultYAML` in `internal/config/defaults.go` — update it
whenever config fields change.
